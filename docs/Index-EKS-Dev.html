How we built Kubernetes on EKS

1

IAM roles — setting the rules of access

AWS IAM

Before anything else existed, we created two identity roles. One for the cluster's control plane, and one for the worker servers. Each role is only allowed to do its own job — nothing more.

Why first: every AWS resource we create next needs to say "who is allowed to touch me," so the permissions have to exist before the things that use them.
# eks-cluster-role → policy: AmazonEKSClusterPolicy # eks-node-role → policies: AmazonEKSWorkerNodePolicy, AmazonEKS_CNI_Policy, AmazonEC2ContainerRegistryReadOnly
2

The EKS cluster — building the control plane

Amazon EKS

The cluster is the brain: the system that tracks what should be running and where. We used Amazon's managed Kubernetes, EKS, attached it to eks-cluster-role, and pointed it at our existing VPC and subnets.

We turned off "EKS Auto Mode," a newer automatic-management setting, since it asks for extra permissions our simple setup did not need.
3

Node group — adding real servers

EC2 / EKS

The control plane alone runs nothing. It needs real servers, called nodes, to place containers on. We added a node group using eks-node-role, sized t3.small, in the private subnet.

Our first attempt used a free-tier instance type and failed outright with a launch error, and the smallest free size was too short on memory anyway — t3.small fixed both problems.
4

Connecting kubectl — giving ourselves the controls

Local machine

kubectl is the command line tool used to actually talk to the cluster. We pointed it at oilgas-cluster, and confirmed both nodes showed up as Ready.

$ aws eks update-kubeconfig --region us-east-1 --name oilgas-cluster $ kubectl get nodes ip-10-0-2-226 Ready ip-10-0-2-84 Ready
5

OIDC provider — linking cluster identity to AWS

eksctl

Before installing anything that needs AWS permissions, the cluster needs a trusted way to prove its identity to AWS. This one command creates that trust link.

$ eksctl utils associate-iam-oidc-provider \ --region us-east-1 --cluster oilgas-cluster --approve
6

Controller policy — defining what it's allowed to do

AWS IAM

The AWS Load Balancer Controller will need permission to create real load balancers later. We downloaded AWS's official permission list for it and turned that into an IAM policy.

$ curl -o iam-policy.json .../iam_policy.json $ aws iam create-policy \ --policy-name AWSLoadBalancerControllerIAMPolicy \ --policy-document file://iam-policy.json

7

Service account — handing the permission to Kubernetes

eksctl

A service account is Kubernetes' own internal identity. This command creates one named aws-load-balancer-controller, and links it to a new AWS role carrying the policy from the previous step.

$ eksctl create iamserviceaccount \ --cluster=oilgas-cluster --namespace=kube-system \ --name=aws-load-balancer-controller \ --role-name AmazonEKSLoadBalancerControllerRole \ --attach-policy-arn=<policy ARN> --approve
8

Installing with Helm — bringing the controller to life

Helm

Helm is a package manager for Kubernetes. One install command deploys the AWS Load Balancer Controller itself as a running workload inside the cluster, using the service account we just created.

$ helm install aws-load-balancer-controller \ eks/aws-load-balancer-controller -n kube-system \ --set clusterName=oilgas-cluster \ --set serviceAccount.create=false \ --set serviceAccount.name=aws-load-balancer-controller $ kubectl get deployment -n kube-system aws-load-balancer-controller READY 2/2
9

Tagging subnets — telling AWS where traffic can land

VPC

The controller needs to know which subnets are allowed to carry public traffic, and which are internal-only. We tagged our two public subnets for public load balancers, and the private subnet for internal ones.

public subnets → kubernetes.io/role/elb = 1 private subnet → kubernetes.io/role/internal-elb = 1

Deploying the workloads

kubectl apply

With the cluster and controller ready, we applied our configuration files in order: the database secret, the database itself, the private API, and finally the dashboard.

$ kubectl apply -f k8s/db-secret.yaml $ kubectl apply -f k8s/database.yaml $ kubectl apply -f k8s/api.yaml -f k8s/api-internal.yaml $ kubectl apply -f k8s/dashboard.yaml

11

Ingress → ALB — from rule to real address

AWS ALB

An Ingress is only a rule: "public traffic should reach the dashboard." The moment we applied it, the Load Balancer Controller (step 8) noticed it and automatically created a real Application Load Balancer in the public subnets, generating a public address.

$ kubectl apply -f k8s/ingress.yaml $ kubectl get ingress ADDRESS oilgas-alb-xxxxx.us-east-1.elb.amazonaws.com
ALB address generated
12

Adding CloudFront — the secure front door

Amazon CloudFront

The ALB by itself only speaks plain, unencrypted traffic. We placed CloudFront in front of it as a free way to add HTTPS, with no domain purchase needed — caching turned off, since dashboard data changes constantly.
